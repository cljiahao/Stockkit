# Customer-return movement reason

## Problem

`stock_movements.reason` is constrained to `restock` / `waste` / `adjustment` /
`initial` (the CHECK constraint in `supabase/migrations/0001_initial_schema.sql`).
A customer returning an unused item to a vendor doesn't map cleanly to any of
these — it's not `restock` (implies bought from a supplier, and
`stock-log-form.tsx` pairs `restock` with a "unit cost this restock" field
that a return doesn't have), not `adjustment` (implies correcting a counting
error, not a real transaction), and not `waste`/`initial`. Vendors currently
have to misuse `adjustment` and rely on the free-text `note` to explain a
return after the fact — the ledger itself can't answer "how much of my stock
movement this month was returns?" without parsing notes by hand.

## Design

Add `'return'` as a fifth reason:

1. **Migration** (next file in `supabase/migrations/`): CHECK constraints
   can't be altered in place, so drop and recreate it:
   ```sql
   ALTER TABLE stockkit.stock_movements
     DROP CONSTRAINT stock_movements_reason_check;
   ALTER TABLE stockkit.stock_movements
     ADD CONSTRAINT stock_movements_reason_check
     CHECK (reason IN ('restock', 'waste', 'adjustment', 'initial', 'return'));
   ```
   (Constraint name assumed from Postgres's default `<table>_<column>_check`
   naming — confirm the actual name via `\d stockkit.stock_movements` before
   writing the migration, since an unnamed CHECK's autogenerated name isn't
   guaranteed.) No RLS/grant changes — `record_stock_movement`'s existing
   INSERT already accepts any value the CHECK allows.
2. **`src/lib/schemas.ts`**: add `'return'` to `stockMovementFormSchema`'s
   `reason` enum.
3. **`src/lib/types.ts`**: update the hand-maintained `stock_movements.reason`
   type union to match.
4. **`stock-log-form.tsx`**: add a `return` entry to the `Reason` type and
   `REASON_LABEL` map, a `<SelectItem value="return">Return</SelectItem>`,
   and treat it as a positive delta alongside `restock` in the `sign`
   calculation (`reason === 'restock' ? 1 : ...`). Unlike `restock`, a return
   doesn't need the "unit cost this restock" field — that field's visibility
   already gates on `reason === 'restock'` and should stay that way, since a
   returned item's cost is the product's existing `unit_cost_cents`, not a
   new purchase price.

## Out of scope

Return-reason-code taxonomies (defective vs. changed-mind), restocking fees,
linking a return back to the original sale/order (stockkit has no order
concept — that's qkit's), and exchange workflows (return + immediate
re-purchase as one action).
